Problem

Three controllers (HydrationController, WorkoutController, FoodLogController) are shallow — their Interface is close to their Implementation (list mutation + cache invalidation + DB write + callback). Cache-date semantics leak through constructor Seams (_isCacheValid, _currentCacheDate callbacks).

Solution

Make "today nutrition/activity state" a deeper Module that owns date boundaries, cache policy, persistence coordination, and side effects (health sync, widgets, streaks) behind one Interface. Keep the controllers as internal seams only.

Wins

  • Locality: day-boundary & rollover bugs live in one place
  • Leverage: one Interface, six side-effect paths
  • Deletion test: deleting HydrationController inlines ~80 lines; deleting NutritionDayState loses real orchestration
  • Tests: one seam covers date rollover, health sync, streak, widget updates

Collapse food logging intake into a deeper Module

Strong in-process
lib/services/food_entry_factory.dart · lib/ui/screens/barcode_scanner_screen.dart · lib/ui/screens/food_search_screen.dart · lib/ui/screens/nutrition_label_scanner_screen.dart · lib/ui/components/quick_add_sheet.dart · lib/ui/screens/add_food_screen.dart · lib/ui/screens/ai_food_camera_screen.dart · lib/ui/screens/meal_detail_screen.dart · lib/providers/nutrition_provider.dart

Before

After

Problem

FoodEntryFactory is shallow — its Interface repeats FoodEntry/FoodItem fields. The real Implementation of "log this food" is duplicated across 7+ screens: each builds the entry, calls addFoodEntry, calls addRecentFood, and pops navigation. The Seam between UI and nutrition domain is leaky — screens must know grams, display names, side effects, and meal assignment.

Solution

Move food logging into a deeper Module that expresses user intent ("log barcode product X at Y grams for meal Z"). Screens declare what was found; the Module owns entry construction, display naming, recent-food persistence, custom food creation, and navigation decision.

Wins

  • Locality: one place for display-name bugs, missing recent-food, meal misassignment
  • Leverage: every intake path (barcode, search, label, manual, AI, import) benefits from one policy
  • Tests: test intake policy without widget harnesses — one seam covers all paths
  • Deletion test: deleting FoodEntryFactory just moves constructor calls; deleting FoodIntakeController loses real orchestration

Problem

Progress photo lifecycle is scattered: controller owns file writes/deletes, provider owns the in-memory list, export serialises metadata only, screens derive thumbnail paths by string replacement. Import calls restoreProgressPhoto which bypasses file lifecycle entirely — imported photos reference nonexistent files. Absolute paths break OS backup portability.

Solution

Consolidate path policy, file lifecycle, metadata lifecycle, export/import restoration, orphan cleanup, and comparison selection into one deeper Module. UI requests photos by ID; the Module resolves paths.

Wins

  • Locality: file-missing, orphan, restore, and path portability bugs live together
  • Leverage: UI, dashboard, compare, and export reuse the same photo rules
  • Tests: addPhoto/deletePhoto/import/export/comparison testable through one Interface
  • Docs alignment: relative paths and image export/import match the plan

Problem

BarcodeLookupService has real Depth internally (multi-source chain, caches, TTLs), but its Seam leaks correction details upward. PortionPickerSheet calls saveUserCorrection and resetCorrection directly, reads BarcodeLookupData, and orchestrates rehydration. The UI is an Adapter for correction lifecycle.

Solution

Keep correction/reset/cache inside the barcode Module. The UI asks "edit product for this barcode" or "reset to original" — the Module decides what to invalidate, refresh, or persist. UI receives an updated FoodItem without knowing the cache mechanics.

Wins

  • Locality: correction/reset/cache bugs stay in the barcode Module
  • Leverage: any barcode entry point gets the same correction behavior
  • Tests: existing barcode tests can cover more user-correction flows without widget tests
  • Interface shrinks: UI stops knowing saveUserCorrection/resetCorrection/cache status

Problem

NutritionLabelParser has useful Depth and tests. NutritionLabelScannerService is a shallow Adapter (69 lines) — its Interface scanLabel(File) makes OCR behaviour hard to test independently. The screen constructs service, Gemini fallback, converts results to FoodItem, generates servings, then calls FoodEntryFactory + NutritionProvider. The pipeline leaks across screen + scanner + factory.

Solution

Separate "understand a label image" from "turn the result into a loggable product." A deeper Module owns: OCR abstraction, parsing, Gemini fallback policy, product conversion, and food logging, behind one processImage(File) → LogResult Interface.

Wins

  • Locality: parser/fallback/product-conversion bugs isolate in one Module
  • Leverage: barcode-not-found label scanning and dedicated scanner reuse the same pipeline
  • Tests: feed OCR text directly, test Gemini fallback decisions, test product conversion — no camera or files needed
  • Interface shrinks: screen stops knowing OCR, parser, Gemini, servings, factory

Problem

PlannedMealFactory is partly shallow constructor mapping and partly hidden policy (servings scaling, ingredient conversion, category inference via English keywords). MealPlanController handles persistence, date caches, copying, totals, and shopping aggregation, but callers must know which factory method to use and understand meal shape. Category inference leaks across a Seam in the factory, while aggregation lives in the controller.

Solution

Deepen meal planning around "plan a meal" and "derive shopping needs." One Module owns conversion policy, category rules, serving scaling, meal copying, shopping aggregation, and checked-state persistence behind a cohesive Interface.

Wins

  • Locality: shopping/category bugs live near meal-planning rules, not in a factory
  • Leverage: future import, AI recipe extraction, and manual planning reuse the same policy
  • Tests: date range aggregation, copied meals with servings, and shopping categories through one seam
  • Interface shrinks: UI stops choosing factory methods or remembering category heuristics

Top recommendation

Collapse food logging intake into a deeper Module (candidate 2)

This is the highest-leverage candidate because every intake path duplicates logging choreography, the shallow FoodEntryFactory adds no abstraction, and the bugs most likely to reach users (wrong display name, missing recent food, inconsistent meal assignment) are exactly the kind that scatter across 7+ screen files. Deepening here doesn't require schema changes or storage rework — it's pure behaviour consolidation with immediate testability gains. A single FoodIntakeController Interface would serve every scanner, searcher, and manual entry form, and the tests would cover every path without a widget harness.
