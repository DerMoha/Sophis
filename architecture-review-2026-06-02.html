Problem

The two label-intake flows duplicate the preview widget, the NutritionLabelResult → FoodItem conversion, the servings generation, and the Gemini-fallback wiring. The scanner service is a 69-line shallow coordinator with a dead method (analyzeNutritionLabel, 79 lines, zero callers) and a leaked failure sentinel (calories == 0 in two UI files).

Solution

Extract a deeper LabelIntakeFlow module that owns OCR extraction, regex parsing, Gemini fallback policy, FoodItem construction, and ServingSize generation behind a processImage → LogResult interface. One shared LabelPreviewSheet replaces both duplicated preview widgets. Drop analyzeNutritionLabel. Route id generation through FoodIntakeController.idGenerator.

Wins

  • Leverage — one pipeline service, 4+ call sites
  • Locality — the valid-scan threshold collapses from 3 files to 1
  • Deletion — drop ~600 lines (2 preview widgets + dead method)
  • Testability — pipeline becomes a pure text → LogResult function
  • Safety — “calories==0” sentinel no longer leaks to widgets

Problem

Solution

  • Deletion — ~1100 lines del, ~400 added (net -700)
  • Deletable now — home_refresh.dart (14 lines, 0 downstream)

C — Move the notification ID space behind one deeper notifier

Strong ports & adapters
lib/services/notification_service.dart · lib/providers/supplements_provider.dart (magic number constants) · lib/providers/settings_provider.dart (raw id: i) · new: notification_id_space.dart, test/services/notification_id_space_test.dart

Before — magic-number contract in 2 files, enforced by comments

SupplementsProvider
_notificationIdStart = 100;
_maxSupplements = 100;
_notificationIdEnd = 200;
_getNotificationId(id) → 100 + position
reorder() → updateAllNotifications()
  cancels 100 OS notifications, reschedules all
&larrang; comment contract &rarrang;
NotificationService
// Notification ID Ranges:
// 0-99: Meal reminders
// 100-199: Supplement reminders
scheduleMealReminder(id: 2, ...) ← hardcoded 0/1/2

⚠ Real bug: reorder at 8:01 AM demotes 8:00 AM alarm to “tomorrow”

updateAllNotifications() re-evaluates skip-today for every supplement. Positional IDs mean every drag cancels 100 alarms.

After — notifier owns the id space, consumers use stable keys

LocalNotifier
interface: scheduleDaily(key, type, title, body, hour, minute, skipToday)
    cancel(key)
    cancelAllOfType(type)
owns: id space (0-99 meals, 100-199 supplements, 200+ reserved)
  key → id mapping
  duplicate suppression
  skip-today update-in-place
SupplementsProvider uses key: 'supplement:${id}' — stable across reorder
SettingsProvider uses key: 'meal-type:${meal.id}'
Reorder: no-op for notifications (key unchanged)
SupplementsProvider._notificationIdStart — deleted
SupplementsProvider._maxSupplements — deleted
SupplementsProvider._getNotificationId() — deleted
updateAllNotifications() — deleted (reorder is a no-op)

Problem

Notification IDs are a global resource enforced by a comment in two files and a static const _maxSupplements = 100 cap in a third. The SupplementsProvider.reorderSupplements path triggers a full cancel-and-reschedule of 100 OS notifications, with skip-today logic that demotes already-fired alarms to tomorrow. The SettingsProvider uses hardcoded id: i for meal types. No two-adapter test exists for the id space.

Solution

Introduce a LocalNotifier interface that takes (type, string key) and owns the id translation internally. Consumers use stable keys (e.g. 'supplement:${id}'). updateDaily lets the notifier update skip-today in place without a cancel+reschedule. Drop _notificationIdStart, _maxSupplements, _getNotificationId, and the updateAllNotifications call from reorder. Add a two-adapter test for the id space.

Wins

  • Depth — notifier hides id-translation + dedup + skip-today in 5 methods
  • Locality — id-arithmetic bugs live in one tested module
  • Leverage — meals, supplements, future reminder types share the same surface
  • Safety — reorder stops demoting already-fired alarms
  • Seam — second two-adapter seam in the codebase (alongside HealthServiceProtocol)
